# 기능 진행 절차

## 0. 준비
1. `docs/HANDOFF.md`(인계)를 읽고 이어 갈 작업을 확인한다.
2. Linear 이슈가 없으면 만들고 In Progress로 바꾼다(snsg-be `docs/linear-convention.md`). `docs/PLAN.md`에 행을 추가한다.
3. 브랜치 `feature/SHI-<번호>-<작업-이름>`.

## 1. 작업 지시서 — `.claude/tasks/SHI-<번호>.md`
없으면 만든다. 형식:
```
# SHI-<번호> <제목>
## 개요
## 기준 문서        (정의서·화면 명세 절, 시안 파일, USER_FLOW 절, snsg-be api-guide 커밋)
## 화면별 자료      (화면 ID | 화면 명세 md 행 | 정의서 md 행 | 디자인UI 이미지 — 아래 "자료 읽는 법")
## 결정 사항        (날짜와 함께. 사용자가 답하면 바로 옮긴다)
## 열린 질문
## 단계             (- [ ] 1. 할 일 — 확인: 화면 경로·누를 것·기대 결과)
## 대상 파일
## 진행 상태
## 리뷰
```

## 자료 읽는 법 (토큰 절약)
- 기획서 md는 전체를 읽지 않는다. 지시서 "화면별 자료"의 행 범위만 `sed -n '시작,끝p'`로 읽는다. 표가 없으면 처음 한 번 `grep -n`으로 화면 ID 행을 찾아 표를 채운 뒤 쓴다.
- 시안 이미지는 `00_Inbox/디자인UI/`(오른쪽 디자인 UI만 잘라 둔 것, 한 장 약 0.7~0.9k 토큰)를 본다. 원본(와이어프레임 + 디자인, 약 2k)은 와이어프레임과 비교해야 할 때만.
- 새 시안을 받으면 `디자인UI/`에 잘라 넣고 표에 추가한다(원본 왼쪽 절반 = 와이어프레임, 오른쪽 = 디자인 UI). PDF는 직접 읽지 않는다(페이지마다 이미지 + 글이라 가장 비쌈).
- 역할별로 보는 자료:

| 에이전트 | 읽는 것 | 보지 않는 것 |
|---|---|---|
| requirements-analyst | 지시서, md 해당 행, USER_FLOW·DESIGN 해당 절, 디자인UI 이미지(빠진 시안·표시 차이 확인용) | 원본 이미지, PDF |
| ui-implementer | 지시서(결정 사항·화면별 자료), 디자인UI 이미지, DESIGN 해당 절 | 정의서 md(지시서에 옮긴 결정으로 충분) |
| frontend-developer | 지시서, md 해당 행(입력·출력·예외), USER_FLOW 해당 절, api-guide | 이미지 |
| code-reviewer | 지시서, 변경 diff, 관련 규칙 | 이미지·md(UI 대조가 필요한 지적만 디자인UI 1장) |

## 2. 역할별 진행
`.claude/agents/`에 역할 에이전트가 있으면 아래 순서로 맡긴다. 없으면 메인 세션이 같은 순서로 직접 한다.
1. **requirements-analyst:** 문서·시안·코드를 대조해 빠진 것·충돌·미정 항목을 정리한다 → 사용자에게 물어볼 목록으로 보여 준다.
2. **ui-implementer**(공통 UI·Story·스타일)와 **frontend-developer**(API·훅·MSW·폼·라우팅·E2E): 동시에 돌릴 때는 맡을 파일을 나눠 지시서에 적는다.
3. **code-reviewer:** 커밋 전 반드시. 결과는 지시서 "리뷰"에.

- 에이전트에게는 지시서 경로와 이번 단계의 할 일만 준다. 같은 기능 안에서는 이미 띄운 에이전트를 이어서 쓴다.
- 점검만 시킬 때는 "코드 수정 없이 보고만".
- 각 단계를 시작할 때 어떤 에이전트로 진행하는지 사용자에게 알린다.

## 3. 단계마다
- 한 번에 한 단계. 끝나면 `verify` 스킬로 검사하고, 사용자가 직접 확인할 방법을 지시서 "단계"에 적는다. 사용자가 확인하면 `[x]`.
- 정하지 않은 것은 지어내지 않고 물어볼 목록으로 보여 준다.

## 4. 마무리
1. code-reviewer → 고칠 것 반영.
2. 문서(USER_FLOW·DESIGN·TECH_STACK)에 결정 반영.
3. `flow-report` 스킬로 화면 흐름 아티팩트를 발행해 사용자가 순서대로 확인하게 한다. URL은 지시서에 적는다.
4. `docs/HANDOFF.md` 갱신(다음에 할 일), `docs/PLAN.md` 상태 갱신.
5. 사용자가 요청하면 `pr` 스킬로 커밋·PR.
