# 상태 · API · MSW

## 상태 위치 (TECH_STACK §3.3, §3.7)
| 대상 | 위치 |
|---|---|
| 서버 데이터 (로그인 사용자 정보 포함) | TanStack Query |
| 필터 값, 선택된 탭 | URL 쿼리 파라미터 |
| 로그인 후 돌아갈 화면 | sessionStorage `loginRedirect` |
| 모달 열림, 입력 중인 값 | 컴포넌트 state |

- 서버 데이터를 `useState`로 복사하지 않는다. 전역 상태 라이브러리는 쓰지 않는다.
- API 호출은 **쿼리 훅 → API 함수 → 공통 Axios 클라이언트** 순서. 컴포넌트에서 axios·fetch를 직접 호출하지 않는다.
- mutation(참여·취소·개설)이 끝나면 영향을 받는 쿼리를 무효화한다. 낙관적 업데이트는 쓰지 않는다.

## API 계약
- 기준은 백엔드 저장소 `snsg-be`의 **develop 브랜치** 문서다. 이 저장소에 복사본을 두지 않는다.
  - `docs/api-guide.md`: 동작, 에러 코드, 화면별 처리 / `docs/openapi.yaml`: 요청·응답 필드와 타입
- API를 다루기 전에 `api-contract` 스킬로 최신 문서를 확인한다(fetch와 읽기만, 백엔드 작업 폴더는 바꾸지 않는다).
- 엔드포인트, 요청·응답 필드, 에러 코드, 인증 방식(T-7)을 문서 없이 정하지 않는다.
- 문서에 없는 API가 필요하면 구현 전에 사용자에게 알린다. 임시 계약으로 진행하기로 하면:
  - `features/<기능>/api/` 한 곳에만 두고 `TODO(API): 미확정`을 표시한다.
  - 타입은 USER_FLOW §11에서 화면에 필요한 최소 필드만.
  - 작업 요약·PR에 가정한 계약을 목록으로 적는다.

## MSW
- 쓰는 경우: 백엔드가 준비되지 않은 API로 개발할 때 / 문서에 있는 실패 케이스(중복 참여, 401 등)를 재현할 때 / Story.
- mock은 실제 계약이 아니다. 백엔드 문서 기준으로 만들고, 없으면 임시 계약과 같은 타입을 쓴다. 실제 API가 생기면 환경 변수로 끈다.
- 브라우저 쪽만 mock한다.
